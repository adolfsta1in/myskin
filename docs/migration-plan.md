# План миграции: демо → MVP

> **2026-10-18: приложение переименовано в Velvi** (в App Store — «Velvi: Psoriasis Tracker»). Ниже «MySkin» в описаниях — прежнее название; пути и внутренние имена (`MySkin/`, `MySkinTests/`, `app.myskin.ios`, myskin.cc) остались прежними.

Источники: `docs/current-state.md` (что есть), `docs/spec.md` (что нужно).

Рамки MVP, принятые на сегодня:
- только **псориаз**;
- интерфейс на **английском**;
- без бэкенда: данные хранятся локально;
- состав MVP — по `spec.md` §8: онбординг, чек-ин, карта тела с BSA и особыми зонами, фото по зонам, план лечения и напоминания, DLQI, PEST, красные флаги, отчёт для врача, блокировка.

Решения пользователя (после фазы 2):
- **Фото** — системная камера (`UIImagePickerController`) и медиатека (`PhotosPicker`). Своя камера с контуром-«призраком» — после MVP.
- **Препараты** — встроенный справочник популярных позиций для псориаза и возможность добавить свой.
- **Режим Calm/Flare** — переключается автоматически по данным. Правило — в §1.6.

## 1.5 Модель данных: подробная оценка

### Подходит ли текущая модель под spec?
**Нет.** Пригодна только статическая часть: `BodyZone` (id, площадь), `BodySide`, `InjectionSite`, `TreatmentKind`. Сущностей, которые хранят данные во времени, нет совсем.

| Сущность spec §3 | Есть сейчас | Оценка |
|---|---|---|
| `Profile` | Поля `condition`, `profile`, `goals` в `AppStore` | Переделать: одиночная запись (SwiftData или настройки) с `psoriasisTypes`, `onsetYear`, `skinTone`, `goals` |
| `DailyCheckIn` | `todayItch`, `selectedTags` (без даты) | Создать заново |
| `ZoneAssessment` | `zoneIntensity: [String: Int]` | Создать заново: дата, zoneID, palms, erythema/induration/scale 0–4, pustules |
| `SeveritySnapshot` | `affectedArea` (computed) | Вычислять из `ZoneAssessment`. Хранить не нужно |
| `Photo` | `PhotoEntry` без изображения | Создать заново: дата, zoneID, `fileName`, связь с лечением |
| `Treatment` | struct с `zones: [String]` (имена) и `frequency: String` | Переделать: `@Model` с `kind`, `steroidClass?`, `scheduleKind` + `interval`, `zoneIDs: [String]` (id), `startDate`, `endDate`, `stopReason` |
| `DoseLog` | `TreatmentReminder.isDone`, `lastInjectionSite` | Создать заново: связь с treatment, время, done/skipped, injectionSite, FTU |
| `SideEffect` | — | MVP: свободный текст в `DoseLog` / `Treatment.notes`. Отдельная сущность — v1.1 |
| `QuestionnaireResult` | — | Создать: тип (DLQI/PEST), дата, `answers: [Int]`, `score` |
| `JointLog` | — | В MVP суставы покрываются PEST. Отдельный журнал — v1.2 |
| `HealthMetric`, `LifestyleLog`, `WeatherSample` | — | v1.1–v1.2 |
| `Experiment`, `Insight` | Моки | Удалить из MVP. Insight — вычисляемый (v1.1) |

### Что придётся менять
1. **Стабильные идентификаторы.** Зоны — строковые id (`front.elbow.left`). Триггеры — enum `Trigger: String` + свои теги в отдельной коллекции. Никаких отображаемых имён в данных.
2. **Перечисления — в `Codable` со строковым rawValue.** Значения хранятся строками; новые случаи только добавляются, старые не переименовываются.
3. **Справочник и план разделены.** `Treatment` — запись плана пользователя. Справочник препаратов (если будет) — статический список в коде, не в БД.
4. **Расписание вместо строки.** `scheduleKind` (daily N раз / weekly / every N days / every N weeks) + времена. Из него строятся напоминания и календарь доз.
5. **Даты.** Чек-ин и оценки привязаны к дню (`startOfDay`), одна запись на день с правкой.
6. **Схема с версиями с первого дня.** `SchemaV1` + `MigrationPlan`, чтобы v1.1 и v1.2 добавляли поля без потери данных.
7. **Фото вне БД.** В SwiftData только имя файла. Сам файл лежит в защищённой папке. При удалении записи удаляется и файл.

### Риск потери данных у пользователей демо
**Риска нет.** Демо ничего не сохраняет: ни SwiftData, ни UserDefaults, ни файлов, а запускалось только в симуляторе. Мигрировать нечего, поэтому новую схему можно спроектировать с нуля без совместимости со старой. Смена bundle id тоже ничего не ломает.

Риск появится **после** первой установки MVP с SwiftData. Поэтому версионированная схема нужна сразу (п.6 выше).

## 1.6 Автоматический режим Calm / Flare

Режим — вычисляемое значение (`FlareDetector`, чистая функция с тестами), а не сохраняемое поле. На вход — последние чек-ины и оценки зон.

**Flare**, если выполняется хотя бы одно:
- зуд ≥ 7 сегодня или вчера;
- зуд сегодня на 3 и более пункта выше среднего за 7 предыдущих дней (нужно ≥ 3 чек-ина);
- BSA вырос на 1 и более процентный пункт относительно предыдущей оценки или появилась новая зона;
- в чек-ине отмечено «new or spreading spots».

**Возврат в Calm** — 3 дня подряд без признаков обострения.

**Нет данных** (нет чек-инов и оценок) — Calm. Минимального числа чек-инов нет: любой признак срабатывает с первого чек-ина (решение пользователя, шаг 13.1). Порог ≥ 3 чек-инов остаётся только для правила «выше среднего».

В интерфейсе вместо переключателя — плашка «Flare mode · why?» с объяснением, какое правило сработало. Пороги — константы в одном месте, их легко подстроить.

# Решение (фаза 3): развивать текущий проект или начать новый

## Рекомендация: развивать текущий проект на месте

Слой модели и состояния полностью заменяем. Дизайн-систему и экраны сохраняем и переводим на реальные данные.

## Обоснование

| Критерий | Оценка | Вывод |
|---|---|---|
| Объём переделок | Около 17 файлов. Переписываются `AppStore.swift`, `Models.swift` и логика внутри экранов. Вёрстка экранов, дизайн-система, силуэт тела и каркас онбординга остаются (§1.1) | Новый проект дал бы ту же работу плюс перенос |

| Модель данных | Не подходит, но её **нечем заменять в старом** — пишем новую рядом (`Model/Persistence/`), старую удаляем, когда последний экран переедет | Решение одинаковое в обоих вариантах |
| Риск данных | Нет сохранённых данных и пользователей (§1.5) | Совместимость с демо не нужна ни в одном варианте |
| Настройки проекта | iOS 27, MainActor по умолчанию, String Catalog уже настроены. Нужно поменять: bundle id, team, Swift 6, usage descriptions, добавить тестовый таргет | Правки в настройках, а не причина пересоздавать проект |
| Проверяемость | Демо продолжает собираться на каждом шаге: экраны, которые ещё не переехали, работают на превью-моках | Удобно проверять малыми шагами в Xcode |

**Минус варианта:** имя проекта «Untitled Project» и таргет `MyApp`. Это косметика: переименовать можно позже или оставить. Display name уже «MySkin».

**Когда стоило бы начать заново** (сейчас не наш случай): если бы демо было на UIKit или Combine, с хаотичной навигацией, или если бы дизайн менялся полностью.

## Как проводим замену без «большого взрыва»
1. Новая модель (`@Model`) и сервисы появляются **рядом** со старым `AppStore`.
2. Каждый экран по очереди переводится на `@Query` / новые сервисы. Из `AppStore` удаляется то, что больше не используется.
3. Моки переезжают в `PreviewData` (DEBUG) и наполняют in-memory `ModelContainer` для превью и `DesignCanvasView`.
4. Когда `AppStore` опустеет, он удаляется. Настройки к этому моменту живут в `AppSettings`.

# Часть 2. План работ до MVP

**Правила для каждого шага:**
- один шаг = одна функция или один экран;
- после шага проект собирается (⌘B), тесты зелёные (⌘U), а критерий готовности проверяется в симуляторе;
- шаг не начинается, пока не закрыты его зависимости.

